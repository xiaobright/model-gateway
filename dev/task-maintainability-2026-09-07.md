## 1. 任务范围与执行原则

这是个人、本机使用的小项目。沿用 FastAPI、SQLite、httpx、原生 JavaScript ES 模块和当前启动方式。

本轮实施范围：

1. 继续测试减重，迁移现有行为断言，建立明确的快速验证和真实网络验证入口。

4. 检查路由规则和请求收尾的职责边界，仅在上述修改确实需要时做小幅收敛。

明确不属于本轮：

- 协议转换，以及转换库、转换服务的引入。用户已经确认当前没有需求。

- 前端框架迁移、运行时插件平台、通用依赖注入、事件总线、消息队列、通用 Repository/Service 多层封装。

| K1 | 请求没有模型改名时保留原请求体字节；需要改名时只改变原有规则允许的内容，未知字段、工具参数等继续透传。响应内容不因观察器而改变；不要求压缩编码或 HTTP 网络分块原样保留。 |
| K2 | 现有端点、短路径别名、鉴权覆写、默认请求头、1M 处理、模型列表和 `count_tokens` 行为保持。 |

| K4 | 失败重试仍遵循现有状态码、次数、期限和有状态请求限制。模型级 404 与分组级失败区分；同一次请求不会反复打已经站级失败的分组。 |
| K5 | 上游错误响应头已到但正文不来时，不能堵住后续候选；已经开始向下游输出后，不把另一个上游的回答拼接进去。 |

| K7 | 完成事件后客户端离开与真正的中途断开保持区别；响应头到达与取消相撞时资源也能关闭。一次请求允许多条尝试记录，但最终收尾不能重复或漏记。 |

- 复用 `tests/test_lifecycle.py` 已证明可行的方式，抽取少量公共准备；不要再造一套大型测试框架。

### P3：局部整理前端，先明确状态归属

**本批主范围是“分组编辑 + 拉取模型 + 勾选即录入”。** 当前相关代码跨 `web/app.js` 的 `openGroup`、`saveGroup`、`renderPicker`、`addModels`、`removeModel`、`groupDirty` 和 `ACTIONS` 中的模型操作，并依赖 `web/util.js::state.editingUp/editingGroup`。这里已有具体的异步交错风险，值得集中整理。

#### P3.1 按功能搬一块，不全量拆前端

建议增加一个 `web/group-editor.js`，名称可调整，承担：

- 当前分组编辑会话、所属供应商、表单脏状态和本次拉取结果。
- 打开/保存/移动分组、模型列表拉取、筛选、勾选/取消、批量及手动录入。
- 与这些动作直接相关的 picker 渲染、忙碌状态和错误后的同步。

`app.js` 保留应用初始化、页面导航和集中事件分发，调用这个模块的少量明确入口。通用 `api`、提示和确认框继续复用。全局配置快照可以继续共享；不再把当前编辑目标当成任何异步操作都能随时读取的全局变量。

不要让新模块反向导入 `app.js`，不要出现循环依赖。如果刷新配置确实需要被多处调用，可抽取一个职责清楚的数据刷新模块，或由入口传入一两个具体回调；不要传入整个应用、几十个回调或制作通用控制器框架。相关显示函数可以随功能迁移，也可以接收明确只读参数，避免新模块仍隔空修改别处的私有状态。

候选编辑暂时可留原处。它共用模型列表缓存的部分需要明确接口；只在真实依赖阻碍上述边界时一并小幅整理。概览、图表、日志和动效不作为全量拆分任务。

供应商编辑已有 `upstreamPayload()`，快捷启停与完整保存继续复用它，不能重新造一份漏 `egress` 或请求头的载荷。

#### P3.2 每次异步操作绑定发起时的目标

采用简单的编辑会话序号/请求序号和局部变量即可，不引入状态管理库。至少满足：

| 场景 | 必须达到的结果 |
| --- | --- |
| 在 A 分组拉模型，关掉后打开 B，A 的响应最后到达 | A 的结果不能填入 B、写入 B 的缓存或改掉 B 的状态提示。迟到的失败及 `finally` 也不能影响 B。 |
| 关闭后重新打开同一分组 | 旧编辑会话失效；不能仅比较 group ID 就允许旧结果回写。 |
| 创建/保存 A 尚未返回就切换到 B | 写请求始终指向已捕获的 A；返回的 ID、名称和归属不能覆盖 B 的编辑状态。 |
| 拉取前需要自动保存修改过的 key/接口 | 保存成功后用该次操作确定的分组 ID 拉取。保存失败或编辑会话已变更时，不继续拿旧 key 或另一个分组发请求。 |
| 删除确认框等待期间或批量操作中切换目标 | ID、模型名集合在开始时固定。确认返回时若编辑会话已失效且尚未发出写请求，就结束这次交互；已发出的请求仍按原目标收尾。 |
| 同一条模型操作重复触发 | 对同一项的在途写操作做小范围防重复，失败后恢复可操作状态；不同分组/资源不被全局锁住。 |

补充要求：

- 不需要为了切换页面撤销已经发出的写操作；中断浏览器等待也不代表服务端回滚。写入成功后仍要刷新共享配置，只有当前编辑会话匹配才更新对应弹窗。
- 处理好已有的 `dialog close` 异步事件：旧弹窗的迟到 `close` 不能清掉刚打开的新会话。保留“新建供应商后接着建分组”及叠加弹窗/移动分组的正确目标。
- 拉取结果/失败缓存仍按分组隔离；本批涉及的 key、接口、所属供应商或连接配置改变后，相关缓存应失效，不能把旧结果或一次失败永久沿用。无需新增复杂 TTL 系统。
- 勾选仍立即落库，组名/key/接口仍按保存操作提交；关闭弹窗不假装回滚已录入模型。保存与立即生效的提示保持清楚。
- 外部刷新不得覆写未提交的表单内容；失败后的勾选恢复依据实际库状态。保持现有列表顺序和输入焦点，避免用户连续操作时点空。

#### P3.3 让刷新不会堆积，也不会回写旧快照

现有 `run()` 管按钮忙碌和错误提示，不等于同一资源的请求合并。`refreshConfig`、`refreshOverview`、`refreshStats`、`refreshLog`、`refreshInflight` 应有轻量约束：

1. 某轮请求慢于轮询间隔时，不按计时器无限叠加同类请求。可以合并读取，或只保留一次待补刷新。
2. 请求绑定发起时的参数，例如统计时间窗；旧时间窗的响应不能覆盖新时间窗。
3. **写操作完成后的刷新必须至少包含一次在该写入完成后才发出的读取。** 不能简单返回正在执行的旧 GET promise，让 UI 显示保存前的快照却声称已同步。可以标记失效并在当前请求结束后补读，或使用序号丢弃旧响应；等待调用方应等到有效刷新完成。
4. 重叠入口写同一状态时也要处理先后关系：`refreshConfig` 与 `refreshInflight` 都写 `state.failover`，`refreshStats` 与实时入口都更新 live 计数。不能只给每个函数独立加 busy，就让旧开关/旧计数覆盖新值。选择一个明确写入点或为共享状态使用一致的先后判断即可。
5. 失败释放在途标记，保留最后有效数据并允许重试，不以空数组/默认值清掉可用配置；相关错误给出适度提示。单个接口失败不能永久卡住整个刷新流程。
6. 沿用隐藏页面和打开编辑弹窗时暂停后台轮询的规则，以及当前大致刷新频率。手动保存/取消的必要刷新仍能执行，实时页面的中断按钮不能被无关慢请求阻塞。

不需要通用请求调度器、离线队列或后台同步系统。几处明确的数据域加简单在途/失效标记就足够；实现以能解释上述交错为准。

#### P3.4 前端验证要覆盖真实交互

适合自动验证的部分，用现有 Node 和原生测试能力为实际导出的功能写少量行为检查：会话失效、迟到结果、请求合并和保存后的补读。不要用正则从源文件截取函数体执行，也不要写只检查函数名/代码文本的测试来冒充行为验证。不要为此引入完整浏览器测试平台；确需新增依赖时先证明现有工具无法完成。

浏览器在隔离临时库和本机模拟上游上验证，至少记录以下场景的实际结果：

- 新建供应商后直接新建分组；编辑、保存、移动分组；同一站不同 key 的模型列表分开。
- 拉取、关键词筛选、单项勾选/取消、只操作筛选结果的全选/全不选、手动添加，以及最后候选删除确认。
- 改 key 后拉取会先保存；拉取/保存失败可以重试，未保存表单不会被刷新抹掉。
- 可控延迟的 A/B 分组切换、关闭后重开同一组、旧失败回调，以及保存与已有轮询交错。
- 在慢请求期间多次切换统计时间窗，最终图表对应当前选择；自动降级开关不被另一入口的旧响应改回。
- 现有两种协议筛选、复制分组、候选切换/清冷却、供应商出口快捷启停仍正常。
- 实时页单条 × 中断仍可用，其它流继续，状态最终一致。
- 刷新/重试初始化不会重复绑定事件或启动多组轮询；现有布局、主题、动效和键盘关闭体验保持。

不是每个简单渲染都要新增自动测试。围绕会出错的异步关系留可复现证据，普通样式/文字检查用浏览器完成即可。
