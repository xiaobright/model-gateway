## 当时的详细发现

评审结论：这个项目还没有到需要推倒重写的程度。FastAPI + SQLite + 原生 ES 模块适合个人自用，供应商、分组、路由、协议、故障切换的划分也有实际用途。当时的主要问题是几处状态和统计口径不一致，以及少量异常路径缺少收尾；继续扩展前，值得做一次小范围整理。

本次按 2026-09-07 的工作区实际文件评审，包含已有未提交改动。没有修改应用源码和真实配置。现有测试完整运行一次：81 passed，178.45 秒。浏览器操作使用独立临时数据库和本地模拟上游；补充诊断也只使用临时数据与 MockTransport。此次没有测试真实供应商的服务质量或长期运行表现。

优先修复下面这些具体问题。

1. **[P1] 切换供应商启用状态会清掉出口配置。**

   位置：[web/app.js](../web/app.js)（原记录行号 819）、[gateway/admin.py](../gateway/admin.py)（原记录行号 21）。

   开关提交 PUT 时只带 name、base_url、header_override、enabled，漏了 egress；后端把缺失的 egress 补成空串并写回。浏览器复现：Review A 原先为 direct，取消启用后变成空串，含义变为跟随系统代理。配置了专用代理的站也会受影响。

   最小修改：这条保存路径保留 egress，并复用同一个供应商更新载荷构造函数，避免不同按钮各列一遍字段。以后确实需要局部更新时再增加小型 PATCH 接口，没有必要现在建立通用配置框架。

   验收：分别配置 direct 和代理地址，停用、重新启用后出口及请求头覆写保持原值。

2. **[P1] 为记录错误体而等待，可能阻断故障切换。**

   位置：[gateway/proxy.py](../gateway/proxy.py)（原记录行号 362）。

   已拿到可重试的 503 后，代码先 await resp.aread()，读完整个错误体才尝试备用站。它使用正常模型请求的 600 秒 read 超时；180 秒的限制只在下一次尝试开始前检查。因此错误体卡住时，可能等待很久，最后又因超过期限而不再尝试备用站。

   补充模拟把同一组时间按比例缩短：重试期限 80ms，错误体 150ms 后 ReadTimeout；最终返回 502，只尝试了主站，正常备用站完全未收到请求。这是控制流复现，没有实际等 600 秒。

   最小修改：重试前直接关闭错误响应，或只在很短的独立期限内读取有限的错误摘要；日志采集不能阻塞故障切换。

   验收：主站回 503 头后一直不发正文，备用站仍能被及时调用；普通错误仍有足够的诊断信息。

3. **[P2] 等待上游响应头时，客户端断开没有及时取消关联请求。**

   位置：[gateway/proxy.py](../gateway/proxy.py)（原记录行号 274）、[gateway/proxy.py](../gateway/proxy.py)（原记录行号 311）。

   is_disconnected 只在第二次及后续尝试前检查。第一次 client.send 等响应头期间没有断开监听，relay 的取消处理此时也还没开始。ASGI 信号模拟中，下游断开后 forward 仍在等待，进行中计数保持 1，直到释放模拟上游才收尾。这个验证针对取消联动，并非真实供应商费用验证。

   最小修改：在等待上游期间让断开信号能够取消发送任务，并把响应关闭、进行中注销覆盖到整个请求生命周期。保持每条请求只有一个明确的收尾入口。

   验收：请求体已接收、上游尚未回响应头时取消下游，等待任务与进行中条目能及时结束；已有的流中取消测试仍通过。

4. **[P2] 路由已经自动选到可用候选，界面仍显示“无可用上游”。**

   位置：[gateway/admin.py](../gateway/admin.py)（原记录行号 451）、[gateway/db.py](../gateway/db.py)（原记录行号 915）、[web/views.js](../web/views.js)（原记录行号 317）。

   停用当前选中的主站后，resolve_chain 会跳过停用站并选备用站。但管理接口仅检查 is_active 那条是否启用，给出 active_route_id=null；前端据此报无可用上游。已通过浏览器与实际本地请求同时复现：opus 请求由 Review B 返回 200，页面仍警告无可用上游。

   最小修改：明确区分保存的首选候选和当前可用的起点，管理接口复用路由规则。界面只在没有任何可用候选时显示该警告。涉及冷却时，显示首选和实际尝试状态也应使用一致的含义。

   验收：停用首选但存在启用的备用候选时，页面说明正在使用备用候选；所有候选停用时才显示无可用上游。

5. **[P2] 缓存命中率、成功率和“救回”各用了不同口径。**

   位置：[gateway/stats.py](../gateway/stats.py)（原记录行号 63）、[gateway/stats.py](../gateway/stats.py)（原记录行号 196）、[gateway/admin.py](../gateway/admin.py)（原记录行号 623）、[gateway/db.py](../gateway/db.py)（原记录行号 1046）。

   已复现两个例子：Anthropic 的 input_tokens=100、cache_read_input_tokens=900，被算成 9.0，即 900%，而这个例子应为 90%；只有一条 401 的上游，健康统计仍给出 100% 成功。前者因为 Anthropic 输入字段不含缓存，而计算直接沿用了 Responses 的除法；后者因为 _failed 只把 5xx 和几个异常 note 算失败。

   另外，“救回”仅检查 attempt > 1 和 status < 400，也可能把响应头成功但流被截断的第二次尝试计为成功。两处缓存命中公式还重复实现了一遍。

   最小修改：在统计模块集中成功/失败判定和输入口径。按协议先归一化输入，再聚合缓存比例；Anthropic 有缓存创建字段时也要纳入总输入。客户端主动取消应明确处理，不能在不同卡片上时而成功、时而失败。保留原始 usage 便于排查。

   验收：纯 Responses、纯 Anthropic、混合记录的比例合理；401、429、503、正常完成、截断、主动取消的各项统计一致；失败的第二次尝试不计为救回。

6. **[P2] SSE 观察逻辑依赖字符串位置和网络分块。**

   位置：[gateway/proxy.py](../gateway/proxy.py)（原记录行号 85）、[gateway/proxy.py](../gateway/proxy.py)（原记录行号 423）、[gateway/protocols.py](../gateway/protocols.py)（原记录行号 87）。

   正文中出现字面量 [DONE] 就被 has_end_marker 当成完成；真正未完成的流可能被记成 ok。同一条 hello world 的 delta，整块计为 11 字节，拆成两块后计为 0。当前转发仍会传递这些字节，问题影响结束判定、健康记录和 token 估值，不能把它描述为网关主动丢掉正文。

   最小修改：增加一个小型、每请求独立的 SSE 观察器，保留未完成的帧，按事件类型和独立 data 行判断结束，再统计内容。观察器只负责观测，继续原样转发字节，解析失败也不影响转发。

   验收：任意分块方式得到相同的结束判定和内容计数；正文提到 [DONE] / message_stop 不等于完成；真实结束事件跨块仍能识别。

## 当时对新增接口和代码组织的建议

关于“以后加 completion API 是否简单”，当时的 Protocol 描述符值得保留，但要区分两种范围：

- 仅增加一个新的透传入口：例如 /v1/chat/completions，添加描述符、入口路由、对应的 usage/流事件规则和前端展示信息，现有转发与降级主干可以继续复用。旧的 /v1/completions 也是类似的扩展点。添加格式本身不要求加入格式转换。
- 同一个模型名同时支持 Responses 和 Chat Completions：当前数据库在 [add_model_route](../gateway/db.py)（原记录行号 753） 明确禁止跨接口使用同名模型。若需要这一能力，应把路由身份、首选候选、排序和删除操作按“协议 + 模型名”区分。若暂时可以接受分别起别名，先保留现有结构也可以。

第三种协议还会暴露几处“两种协议”的假设：[复制分组](../gateway/admin.py)（原记录行号 354） 自动选另一个协议；[前端复制按钮](../web/views.js)（原记录行号 627） 用二选一；[筛选按钮](../web/index.html)（原记录行号 90） 写在 HTML 里；[token 估值](../gateway/stats.py)（原记录行号 241） 另外维护协议表。因此 README 的“描述符 + 路由”只概括了后端主干，不能作为完整扩展清单。最小整理是把端点名称、展示信息和相关能力集中登记，让选择器、筛选器和复制目标从名单生成；保持普通函数和 ES 模块即可。

代码组织方面，后端主要压力集中在 [proxy.forward](../gateway/proxy.py)（原记录行号 199），前端集中在约 1266 行的 app.js 和 982 行的 views.js。行数本身不是问题，真正值得调整的是：同一种配置有多条保存路径，同一种状态有多处推导，弹窗操作依赖全局 editing 字段。

建议在下一次改分组功能时，把分组编辑、拉模型、勾选导入及相应渲染收在一个模块；模型路由功能同理。保留 app.js 负责导航和动作分发。db.py 的约 1000 行中有相当一部分是历史迁移，可以单独挪到 migrations.py，现有 SQL 与 SQLite 继续使用。无需为了这些修改引入前端框架、通用插件系统或多层服务架构。

前端视觉已有一致的样式，概览、站点和路由操作也能形成完整流程。近期更有收益的是把反馈做准：保存后配置不意外变化、提示与实际路由一致、进行中状态能正确收尾。轮询还可以增加“上一次未完成就不再发起”的小保护，避免慢响应时请求叠加；表单内即时生效的模型勾选和需要保存的配置应持续清楚区分。此次实际检查了桌面页面，未宣称完成手机布局或所有浏览器的验证。

## 当时的测试耗时

测试确实偏重，但 81 个用例这个数量本身正常。重的是执行方式。

| 观察 | 当前证据 | 含义 |
| --- | --- | --- |
| 完整测试 | 81 passed，178.45 秒 | 接近 3 分钟，作为每次小改后的默认反馈偏慢 |
| 真实网关 fixture | 75 / 81 个用例使用 | 大部分规则都付出了真实服务、端口、HTTP 和清理成本 |
| slow 分类 | 两个文件共 18 个用例整组标 slow | 跳过后仍有 63 个用例，其中 58 个启动网关 |
| 4 个代表用例抽样 | 全通过，pytest 3.89 秒 | 无需再次运行整套就能定位一部分成本 |
| 抽样 TLS 成本 | 12 次证书加载，累计约 1.37 秒 | 甚至仅检查出口参数的测试也在构造真实 transport |
| slow 注释 | 故障切换文件说要等冷却期满，但 11 个用例没有等待到期 | 注释和实际测试不一致，也不能据此声称覆盖了到期恢复 |

拆文件提高了可维护性，没有改变上述执行成本。建议保持三种清晰的验证范围：

1. **日常快速验证**：命名、路由选择、优先级、故障切换规则、统计、SSE 观察等直接测函数；需要数据库时仍使用每例独立的临时 SQLite。时间相关规则用可控时钟，HTTP 响应用 MockTransport。目标可以是几秒到十几秒，这只是优化目标，当前尚未实现。
2. **管理接口验证**：使用进程内 TestClient / ASGITransport 验证校验、配置保存和序列化，不必为每个 400/409 场景启动真实监听端口。模拟函数参数不等于删掉行为断言。
3. **少量真实网络集成测试**：保留流中切换不断流、真实客户端断开、代理实际经过、TLS 证书校验等需要穿过 socket 才能充分证明的路径。相关改动或一批修改完成后再跑。

测试减重时优先迁移现有断言，不要单纯删除 slow 用例，也不要把共享可变数据库改成全套共用来换速度。先给每个阶段记录耗时，做完上述迁移再判断是否需要并行执行。现在无需优先加 pytest-xdist 或额外的测试平台。

建议分三小批完成：先修出口配置丢失、路由误报和统计口径；再修故障切换等待、取消收尾和 SSE 观察，并用轻量回归覆盖它们；之后围绕新增 completion 接口整理协议登记与前端功能模块。每批都可以独立验证和回退，不需要一次性重构全项目。
