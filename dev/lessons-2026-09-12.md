# 9 月 12 日的排查经验

这一天主要解决了两件事：opencode 收不到回复，以及标题生成请求被上游误报。下面先说结论，再列以后能复用的检查方法。

> 这是 2026-09-12 当天的记录。文中的测试数字和站点配置没有在本次文档整理中重新验证。当前操作方法见[维护说明](maintenance.md)。

## 下次怎样少走弯路

### 1. 200 不等于客户端拿到了完整回复

先看响应头的 `content-type` 和 `content-encoding`，再看实际保存的内容。
这次是压缩格式不匹配；下次还可能是上游缺少结束事件、连接中断或客户端解析失败，不能只凭 `truncated` 就定原因。

### 2. 只能向上游声明自己能处理的压缩方式

客户端支持 `br`，不代表网关也支持。网关如果把压缩内容当普通文本发出，再删掉压缩标记，客户端就无法正确读取。
因此 `accept-encoding` 由网关自己的解码能力决定；响应已经解压的部分才去掉相应标记，不能无条件删除整条头。

### 3. 找到一处误报，不代表找全了

同一段提示词可能有多个触发点。应当：找到一处 → 做最小替换 → 重新检查整段 → 仍失败再继续找。
当天第一次只改了一处，请求依然返回 500；后来确认有两处。

检查片段时要隔离其他已知触发文本，否则无论试哪一行都会失败，无法判断是哪行造成的。
分块再缩小范围通常比逐行发送省请求；跨行触发仍需整段复核，不能只靠每行单独通过。

### 4. 排查会花钱，先限制调用量

当天初版探测沿用了抓包里的 `max_tokens=32000`，记录中约 150 次成功请求生成了 16MB 内容。
把生成上限降到 16 后，单次响应约从 100KB 降到 600B，同类排查的输出量降到约 87KB。
这些是当日样本，不是对所有模型的固定比例。

再次排查时，先减少不必要的生成，并给脚本设置 `--max-calls`。请求失败也不能一概认为不计费。

### 5. 文本替换只适合已确认的固定误报

不要为了避开某个站点的误报，随意改文件内容、搜索结果或所有同类符号。
当天 `- `、`→` 单独测试都没有触发，问题出在具体短语；删除所有箭头或列表符号既可能漏报，也会破坏正常文本。

现有规则是全局字符串替换，不是智能审核，也不是密钥脱敏。没有明确需要时保持空表。

## 排查工具怎么找

| 工具 | 入口 |
| --- | --- |
| 临时记录请求和响应 | [抓包步骤与隐私提醒](maintenance.md#抓包排查) |
| 查看抓包状态 | `GET /admin/api/capture-stream` |
| 列出抓包目录 | `GET /admin/api/capture-stream/list` |
| 定位固定文本误报 | `dev/find-sensitive-line.py`，先读[运行限制](maintenance.md#请求文本替换) |
| 配置文本替换 | 管理页「上游站点 → 敏感词绕行」 |

定位脚本会真的发请求，并临时清空替换规则。不要把它当作不影响现有使用的普通检查命令。
