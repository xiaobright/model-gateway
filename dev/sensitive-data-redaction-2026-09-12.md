# 敏感信息过滤方案调研（2026-09-12，未落地实现）

起因：担心请求体里的 apikey / 密钥类内容被上游公益站看到，想找现成开源方案接进网关。
本文是调研记录，供以后真要做的时候直接接着走。

## 0. 结论摘要

- **不要引入现成重型方案**。LLM Guard 已归档；Presidio 方向是 PII（人名/电话/地址）而非密钥，
  中文弱、依赖 spaCy 模型几百 MB，与「轻依赖、无构建步骤」的项目基调冲突。
- 最值得抄的资产是 **gitleaks 的规则集**（`config/gitleaks.toml`）：纯 TOML 数据、200+ 条规则、
  正则 + 香农熵 + 关键词预筛 + 允许清单。项目已功能冻结，但规则是 Go RE2 语法、不支持前瞻断言 ——
  正好是 Python `re` 的子集，可基本原样编译。
- 倾向方案：**不引入任何运行时依赖，自建 `gateway/redact.py`**，内置精简规则集（抄 gitleaks 的
  TOML），纯正则 + 熵，亚毫秒级。
- Yelp detect-secrets（维护中、Apache-2.0）API 面向 `scan_file`，扫内存字符串要绕，且带一堆
  「这是不是测试文件」的过滤器，对非代码内容容易误判 —— 可抄其 detector 正则，不建议直接用。
- Data Maskit（xiaYuTian11/maskit）：形态最接近的完整方案（19 类规则、`{{LABEL_xxxxxx}}` 占位符、
  响应侧流式还原、多轮会话占位符复用），但 AGPL-3.0、它自己就是一个网关，与本项目功能重叠，
  只适合参考设计。

## 1. 关键实现细节（已定位）

- 插入点：`gateway/proxy.py` 的 `forward()`，在 `json.loads(body)` 之后、`db.resolve_chain()` 之前。
- **坑**：`sent_body` 默认等于原始 `body` 字节，只有 `remote != requested` 时才 `json.dumps`
  重建。所以只改 `payload` 会被「字节级透传」分支绕过 —— 脱敏后必须加 `body_dirty` 标记强制重建。
  （2026-09-12 的敏感词绕行层已经踩过同一个坑，加的是 `or rewrite_hits`，可参照。）
- 配置可挂在现有的 `settings` 表（`db.get_setting/set_setting`），作用域建议放在**供应商**一级
  （和 `header_override`、出口同层），因为「哪些站不可信」本来就是站点属性。
- 审计可复用 `request_log`，加一列记命中数。

## 2. 已发现的泄露面（本地静态）

- `data/gateway.db` 的 `groups.api_key` 是明文存储。
- 日志侧目前是干净的：`forward()` 只记 model 名和字节数，不记 body 内容；
  `data/captured_headers.json` 已对 Authorization / Cookie / x-api-key 做 `<redacted>`。
- 抓包（`gateway/capture.py`）落盘的 `request.json` 是**原始请求体**（只对 header 脱敏），
  如果请求体里带密钥，抓包目录里就是明文 —— 用完记得删。

## 3. 敏感数据分类（能否正则识别 × 泄露后果）

- **认得出 + 后果重**（最该拦）：API key、PEM 私钥、数据库连接串、JWT、云厂商 AK/SK、
  webhook URL（Slack/钉钉的 URL 本身就是凭据）。
- **认不出 + 后果重**（只能靠自己）：姓名、学号、工号、客户名单、内部代号、未发布产品名。
- **认得出 + 后果轻**（顺手告警）：手机号、身份证、邮箱、银行卡、内网 IP。
- **认不出 + 后果轻**（不用管）：普通代码、技术讨论。

关键判断：**学号正则做不了** —— 它就是 8–12 位数字，与订单号/时间戳/随机数无法区分。
中文姓名同理，NER 能做但误报高、依赖重。

## 4. 占位符设计的硬约束

- 不能用裸 id（`{{1}}`）：模型会翻译、省略、补全它。要用 `{{PHONE_bcdfgh}}` 语义标签 + 随机后缀。
- **映射必须确定性**（同值 → 同占位符，跨请求稳定）且**持久化到 SQLite**。否则 Claude Code
  滚雪球式上下文里每轮前缀都变 → prompt cache 全废 → 从污染那轮起全程全价计费。

## 5. 实现难度的真实分布

- **请求侧：简单**。forward() 已全量读入 body，遍历字符串值即可，无状态、无额外延迟。
- **响应侧：难，是分水岭**。SSE 逐 chunk，占位符会被 TCP 切成两半 → 需滚动窗口 + 不能立即放行
  （引入延迟）+ 需协议感知（正文 delta vs tool 参数）+ 有状态。
- **最致命的失败模式**：还原不完整时，Claude Code 会把 `{{APIKEY_x7k2}}` **当代码写回用户源文件**。
  不可修复。而静默打码的收益只是「模型能帮你调试那个 key」。

## 6. 定位判断

- 请求侧脱敏**不改变**定位（仍是无状态透传 + 一次内容改写）。
- 响应侧还原**改变**定位：README 明确写「不做格式转换」「完全透明中转」「字节级透传」，
  而还原要求网关必须理解协议语义；并引入内存状态、跨请求生命周期、并发问题。
  **等于从「路由器」变成「中间件」**。
- 代码量三四百行不算多，但**长期维护成本**重：每加一种协议或流事件类型都要回头复查还原逻辑。

## 7. 建议（四层，按性价比排序）

1. 请求侧**只告警不改写** —— 零风险，且让你知道何时该去吊销 key。
2. **本地预防**（根治）—— `.env` / `credentials` 加进 Claude Code ignore，别把 key 放在会被
   `cat` 到的地方。
3. **数据驱动决策**（最符合本项目路子）—— 先加只读探测器跑一两周，统计真实命中率与误报率，
   再决定要不要拦。
4. **选择性阻断** —— 只对强前缀规则（PEM / `sk-ant-` / `AKIA`）拦；`generic-api-key` 这类
   宽泛规则只用于告警。

结论倾向：**「自己注意」是主要防线**，网关脱敏是补充。凭据泄露可修复（吊销重发十分钟），
静默打码搞坏数据不可修复。
