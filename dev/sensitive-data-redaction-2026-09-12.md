# 是否自动隐藏请求里的密钥：调研记录

日期：2026-09-12。**尚未实现，没有开启自动脱敏。**

问题很直接：把代码、对话交给外部 AI 站点时，里面可能夹着 API Key、密码或个人信息。能不能由网关先发现并处理？

## 先看结论

- **现有网关不会自动隐藏请求正文中的秘密。** 「敏感词绕行」只是手写替换规则，不是这个功能。
- 找明显的密钥格式相对容易，但不能识别所有秘密，也会有误报。
- 自动替换后再还原更难：模型可能改坏占位符，工具调用可能把占位符写进源文件。不能只看“替换几行文本”来估工作量。
- 如果以后要做，先考虑检测和明确提醒，再决定是否拦截高置信度的密钥。**本记录不是实施授权，也没有已经选定的方案。**

## 现在需要注意的地方

| 位置 | 风险 |
| --- | --- |
| `data/gateway.db` 的分组密钥 | 明文存储，数据库及备份不能公开。 |
| 发给上游的请求正文 | 包含的代码、对话和工具结果可能带秘密，现有网关不会自动找出它们。 |
| 抓包里的 `request.json` / 响应文件 | 会保存正文，可能留下同样的秘密。 |
| 日志和请求头诊断 | 常规日志主要记录模型、状态和大小，部分鉴权头会过滤；这不等于所有错误文本、未知请求头都保证安全。 |

因此，分享日志或抓包前仍要检查内容。不要因为“请求头已脱敏”就上传整个目录。

## 当时看过哪些开源工具

下表整理原调研的取舍。**本次文档整理没有重新核验这些项目的维护状态、许可证或规则数量**；真要引入时必须再查。

| 工具 | 可以借鉴什么 | 为什么当时没直接接入 |
| --- | --- | --- |
| Gitleaks | 常见密钥的匹配规则、关键词预筛、允许清单和随机性评分 | 更适合作为规则来源。Go 和 Python 的正则兼容性要逐条验证，不能承诺全部直接可用。 |
| Yelp detect-secrets | 各类密钥检测方法 | 原调研认为其文件扫描接口和代码文件过滤逻辑不太适合直接扫描任意请求正文。 |
| Presidio | 人名、电话、地址等个人信息识别 | 不是专门的密钥检测器；模型依赖、中文效果和误报需要评估。 |
| LLM Guard | 输入检查的整体思路 | 原记录称项目已归档；采用前需重新核实，不作为现成依赖推荐。 |
| Data Maskit（xiaYuTian11/maskit） | 文本占位符、流式还原、多轮复用 | 本身也是网关，与本项目重叠；原记录标注 AGPL-3.0，使用前需确认许可要求。 |

原先“精简规则、尽量不加重依赖”的方向仍可作为候选思路，但尚未验证准确率、延迟或长期维护成本。
不把“亚毫秒”“几百行”这类估计当作性能或工期保证。

## 哪些内容容易识别，哪些不容易

- **格式比较明显**：带固定前缀的 API Key、PEM 私钥、某些数据库连接串、JWT、带凭据的 webhook 地址。
- **只看文本很难可靠判断**：姓名、学号、工号、客户名单、内部代号、未发布产品名。一个数字串可能是学号，也可能是订单号。
- **格式能认，仍要看用途**：电话、邮箱、身份证号、银行卡号、内网地址。识别出来不等于可以认定它“不重要”。

个人信息和商业秘密都可能造成严重后果。风险大小不能只按“能否用正则找到”排序。

## 四种处理方式的区别

| 方式 | 好处 | 代价或限制 |
| --- | --- | --- |
| 只提醒，不改请求 | 不改变模型看到的内容，便于先了解真实误报率 | 如果仍发给上游，泄露并没有被阻止；提醒本身也不能打印完整密钥。 |
| 检出后拦截 | 可以阻止明显的密钥继续发送 | 误报会打断正常工作，需要清楚的提示和人工处理方式。 |
| 替换成占位符，不还原 | 上游看不到被替换的原值 | 模型可能按占位符生成错误代码或命令，不能静默进行。 |
| 替换后再还原 | 希望既隐藏原值，又保留客户端使用方式 | 要处理流式分块、工具参数、多轮历史、并发和映射保护，最容易出错。 |

发现泄露应尽快吊销或轮换凭据，并检查影响范围；不能保证“换个 Key 就没有后果”。
同样，占位符写坏文件也不一定不可恢复，但会增加检查和修复成本，不能忽略。

## 如果以后真的要实现

以下是供开发者查阅的注意点，不是已经完成的功能。

### 请求侧

- `gateway/proxy.py` 的 `forward()` 已读取 JSON 请求，可以在发给上游前检查字符串。
- 只改解析后的 `payload` 不够：转发有沿用原始 `body` 的分支。内容变化时必须重建发送字节，现有文本替换的 `rewrite_hits` 处理可作参考。
- 是否按供应商启用需要单独决定。现有「敏感词绕行」是全局规则，不能直接当成供应商级隐私开关。
- 不要把检测到的完整密钥写进日志。即使只记命中数，也要先决定告警怎样让用户看见。

### 响应侧还原

占位符可能被拆进不同响应片段，也可能出现在工具参数里；模型还可能改写、删除或复制它。
要做可靠还原，需要额外的缓冲和状态，不能承诺零延迟，也不能只替换聊天正文。

同一会话内稳定的占位符有助于保持上下文一致，但跨会话是否共享、是否持久化、如何过期都要单独设计。
映射表本身含秘密，需要保护，不能为了缓存命中把所有原值长期保存在一个全局表里。

新增这类功能会扩大网关对请求和响应内容的处理范围，协议变化后也要持续维护。应先证明实际收益值得这些成本。

## 不等实现也能做的事

1. 不把真实密钥写进提示词、示例代码、截图或提交记录；测试用明确的假值。
2. 在客户端里设置合适的文件访问限制，避免读取凭据文件，并确认这些限制实际生效。仅写进 `.gitignore` 不等于 AI 不能读取。
3. 对敏感项目选择信任的服务，必要时不要发送相关数据。
4. 分享诊断材料前检查正文，不只检查请求头。

是否增加检测、提醒、拦截或还原，以及作用于哪些供应商，仍需另行决定。
